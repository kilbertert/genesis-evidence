# 0003: Anchor recommendations under confirmed findings

Status: Accepted

Date: 2026-08-28

Parent: PRD #103

## Context

The existing evidence path already turns confirmed observations into risk findings with a canonical `condition_code`. Introducing a second disease-matching step for products would re-derive semantics that the confirmed finding has already established.

## Decision

Recommendations are generated by a deterministic pure function `recommend(condition_code, confirmed_observations)` and attached to the existing finding as `recommendations[]`. The function reuses the finding's `condition_code` and does not perform second-order disease matching. Both finding assembly seams — `ReportStore.assess()` and `EvidenceStore.match_published_cards()` — call the same engine.

## Alternatives Considered

- Independently match raw observations to products: preserves an isolated module but duplicates condition logic and creates divergent results.
- Place recommendations on a separate API route: separates responsibilities but forces the patient UI and evidence envelope to join findings with a second request.
- Put AI classification at runtime: would fit broad catalog coverage but violates the deterministic runtime requirement and audit reproducibility.

## Rationale

The finding is the only patient-meaningful anchor, and its `condition_code` already carries the confirmed clinical-risk mapping. A single pure-function seam keeps both report and Health-Flow entry points consistent, easier to test as external behavior, and deterministic under contract and forbidden-copy guards.

## Consequences

Product matching can only be as good as the finding's condition/severity metadata, so review-published mappings must be versioned and auditable. Any emergency/high-severity suppression and age gating belong in the shared engine, not in entry-point-specific branches.
