# 加购深链契约：health-flow → 商城

Status: Draft — 待商城侧确认（本仓签发端尚未实现）

关联：health-flow #174（检测页商品展示，已交付）、genesis-evidence #159（闭环总规格）。
本文件是**交付给商城侧的接口契约**，与 `docs/condition-to-mall-tag.md` 同类：
它只声明本仓构造什么、需要商城侧做什么，**不记录商城侧的内部实现**。

## 目的

患者在检测页点「加入购物车」时，本平台**不写商城状态、不自建购物车**，而是把患者
**深链回商城**，由商城完成加购。深链携带足够的上下文（本次检测、商品、数量、租户），
并让商城能把该笔订单标记为「来自健康建议」。

契约必须先于实现存在，因为双边的接口今天**不存在**，且有三处不能靠猜（下三节）。

## 需求侧的前提：允许一次商城登录

**原始验收项是「跳过去就能加购，用户无需二次登录」。经与需求方确认，该项已降级为：**

> 点「加入购物车」跳到商城，**以商城侧现有的加购入口完成加购**；若患者在商城侧的会话
> 已失效，**允许其先登录商城，不视为链路失败**。

原因：**商城侧今天没有「无需登录即可加购」的入口**。商城现有的加购入口要求**已登录的
商城会话**——这不是参数问题，缺会话就无法加购。因此「免登录」不是本平台能单方面提供的，
本平台也不要求商城为此新建一条免登录路径。

连带地，深链的职责收窄为**把用户与归因信息带到商城**；「不调用商城任何写接口、不持有
购物车状态」这一条不变。

## 阻塞项一：商城侧需要指定加购入口

深链要跳到一个**商城的加购入口**，其形态由商城侧指定。两条可行方向（**由商城侧选**）：

| | 方向 | 说明 |
| --- | --- | --- |
| **A** | 商城提供一个**能带票据/参数的加购页 URL**，页面内以商城会话完成加购 | 若患者会话仍有效则无感；失效则触发一次商城登录（按上述降级后的验收项，可接受） |
| **B** | 商城新增一个**接受本平台票据**的加购端点 | 工作量在商城侧，可完全免登录；本平台不要求 |

本平台**不代选**，也不需要商城实现的细节；契约只需要一个可构造的 URL 形态。

## 阻塞项二：归因字段由商城侧指定

订单需要一个承载「来自健康建议」的**归因载荷**。本平台**不指定**写在哪个字段，
原因是「订单上哪个字段可写、且能读回来」是商城侧的领域知识，本平台无权也不应决定。

**请商城侧指定：**

1. 归因写入**哪个字段**（自由 JSON 的载体）；
2. C 端**从哪个接口**能把它读回来（若读不回来，链路仍成立，只是「订单来自健康建议」
   这一项对用户不可见）；
3. 该字段**是否已被其他业务占用**——若已占用，请指定替代字段。

**本平台对契约的一处硬要求**：该字段的**可见性与语义由商城侧决定，可能随版本变化**；
因此本平台的归因展示**必须容忍它消失**——读不到时不影响加购本身，也不报错。

## 阻塞项三：深链给不出完整商品标识

**本平台持有的是 SPU 标识（商品级），而加购需要 SKU 标识（规格级）。**
第三方只读商品端点返回的是 SPU，不返回 SKU；SKU 的解析因此**归商城侧**
（商城商品页本来就要完成这件事）。

所以深链携带 **SPU**；若商城侧要求深链直接带 SKU，请提出——本平台需要先拿到 SKU 列表
的来源，那会改变第三方只读端点的返回面，属另行立项。

## 深链形态

```
GET https://<商城域名>/<加购入口路径>
      ?tenant_id=<租户标识>
      &spu_id=<SPU 标识>
      &quantity=<数量>
      &detection_id=<本次检测标识>
      &exp=<过期时间戳（UNIX 秒）>
      &sig=<HMAC-SHA256 签名，十六进制小写>
```

- `<加购入口路径>`：**待商城侧指定**（见阻塞项一）。
- `detection_id`：本平台侧检测记录的标识。**它不保密**——会随报告回显给患者。
  **因此安全性完全依赖 `sig`，不依赖不可猜测。** 这一条是本契约最重要的约束。

## 签名

- 算法：**HMAC-SHA256**；签名方为 **本平台**；密钥**只在本平台与商城之间**持有。
- 待签串：除 `sig` 外的**全部参数**按键名 **ASCII 升序**拼 `k=v`，以 `&` 连接，
  **不做 URL 编码**，末尾不追加密钥以外的内容。
- 参数值先 `trim`；空值不参与拼接。
- 输出：十六进制**小写**，放入 `sig`。
- 密钥交换方式：**待商城侧指定**（本平台不通过明文信道具传递密钥）。

## 过期与失败

- `exp` 为 **UNIX 秒**，有效期 **10 分钟**。**过期校验在商城侧**——本平台签发后无法撤回，
  撤销只能依赖短有效期。
- **两类失败必须分清，否则会出现两套说法：**
  - **商城侧拒绝**（过期、签名不符、商品下架、库存不足）：应在商城侧呈现**用户可见的
    原因页面**。本平台在跳转前**无法预知结果**，故不对此负责。
  - **跳转本身失败**（URL 构造不出、密钥未配置）：由本平台**在跳转前**如实提示，不静默。

## 商城侧需要做什么（汇总）

1. 指定 `<加购入口路径>`（阻塞项一的方向 A 或 B）。
2. 指定归因字段及其读回接口；确认是否已被占用（阻塞项二）。
3. 指定密钥交换方式。
4. 实现 `sig` 与 `exp` 校验，并在拒绝时提供可见的错误页。
5. 解析 SKU（阻塞项三）。

## 本平台要做什么（尚未实现）

- 构造上述 URL 与 `sig`；**不调用商城任何写接口、不持有购物车状态**。
- 密钥只从环境注入；缺失时**不跳转**并如实提示，不发一个注定被拒的链接。
- 单测钉死：篡改任一参数必须验签失败；`exp` 过期必须失败。
- 前端按钮的落地位置等本契约定稿后再做。

## 未验证事项

- **商城 H5 实际发起的加购请求形状**：未验证（本平台只读了服务端源码，未读 H5 前端）。
  需要商城侧或前端团队确认。
- **「患者在商城侧始终已登录」**：无证据。方向 A 的可用性依赖它，方向 B 不依赖。
- **微信内置浏览器中的深链跳转行为**：未验证。商城 H5 为 uni-app 打包，跳转行为可能与
  普通浏览器不同；本平台的既有经验表明这类差异确实存在（报告页在微信内置浏览器下打印受限，
  需引导用户改用系统浏览器）。
- **归因载荷能否在所有下单路径落地**：本平台只验证过普通商品下单路径。
  其他下单类型（积分、奖品、线下、分销等）是否携带归因字段，**未验证**——
  不应假设「任何下单路径都能带归因」。
