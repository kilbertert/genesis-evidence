# 加购深链契约：health-flow → 商城

Status: Draft — 待商城侧确认（本仓签发端尚未实现）

关联：health-flow #174（检测页商品展示，已交付）、genesis-evidence #159（闭环总规格）。
本文件是**交付给商城侧的接口契约**，与 `docs/condition-to-mall-tag.md` 同类：
它只声明本仓构造什么、需要商城侧做什么，**不记录商城侧的内部实现**。

## 目的

患者在检测页点「加入购物车」时，本平台**不写商城状态、不自建购物车**，而是把患者
**深链回商城**，由商城完成加购。深链携带足够的上下文（本次检测、商品、数量、租户）。

**本次交付的形态是「跳到商品详情页，由用户完成加购」**——一次点击即完成加购需要商城
H5 侧的配合改动，不在本次范围内（见「签名担保什么、不担保什么」与「未验证事项」两节）。

契约必须先于实现存在，因为双边的接口今天**不存在**，且有三处不能靠猜（下三节）。

## 需求侧的前提：允许一次商城登录

**原始验收项是「跳过去就能加购，用户无需二次登录」。经与需求方确认，该项已降级为：**

> 点「加入购物车」跳到商城，**以商城侧现有的加购入口完成加购**；若患者在商城侧的会话
> 已失效，**允许其先登录商城，不视为链路失败**。

原因：**商城侧今天没有「无需登录即可加购」的入口**。商城现有的加购入口要求**已登录的
商城会话**——这不是参数问题，缺会话就无法加购。因此「免登录」不是本平台能单方面提供的，
本平台也不要求商城为此新建一条免登录路径。

连带地，深链的职责收窄为**把用户带到商城**（本期**不**携带归因，见阻塞项二）；
「不调用商城任何写接口、不持有购物车状态」这一条不变。

## 阻塞项一：商城侧需要指定加购入口

深链要跳到一个**商城的加购入口**，其形态由商城侧指定。两条可行方向（**由商城侧选**）：

| | 方向 | 说明 |
| --- | --- | --- |
| **A** | 商城提供一个**能带票据/参数的加购页 URL**，页面内以商城会话完成加购 | 若患者会话仍有效则无感；失效则触发一次商城登录（按上述降级后的验收项，可接受） |
| **B** | 商城新增一个**接受本平台票据**的加购端点 | 工作量在商城侧，可完全免登录；本平台不要求 |

**⚠️ 2026-10-01 实测补充**（详见 `artifacts/service-host/acceptance-20261001-mall-order-loop.md`）：
方向 A 有一个**必须由商城侧解决**的硬阻塞——**服务端认会话不等于前端认登录态**。
实测中，深链带着有效票据落地商品页，**商品完整渲染**（价格、库存、名称都在），
但点「加入购物车 → 确定」弹「您还未登录」。原因是商城 H5 的提交分支读的是
localStorage 的 `user_info` **对象**，而不是 `third_session`；票据建立的会话只被
服务端认到，前端登录态是空的。因此方向 A 要真实可用，商城侧必须**由深链接受的
票据/会话建立前端可读的登录态**，否则用户「能看不能买」，只能回退到二次登录。
这条不是本平台单方面能满足的。

本平台**不代选**，也不需要商城实现的细节；契约只需要一个可构造的 URL 形态。

## 阻塞项二：订单归因 —— **本期不做，商城侧无需为此改动**

> **2026-10-01 决定：本平台不实施订单归因。**
> 这一段此前是一份「请商城侧指定归因字段与读回接口」的**请求**，现已**撤回**——
> 不对商城侧提出任何归因相关的要求。下面只保留记录与重启条件。

订单归因（在订单上标记「来自健康建议」）经评估后**决定不做**，理由：

1. **需求侧未确立。** 闭环规格把归因的 C 端展示写成「**仅当**需要展示『本单来自健康建议』
   **时才**需要」——它是条件项而非必备项；到今天**没有被点名的消费者**
   （无报表、无分佣/风控规则、无客服或 C 端页面要读它）。
2. **代价与收益不成比例。** 实现它要么触碰**共用底座库**（会牵连跨仓版本发布），
   要么退到浏览器本地暂存、接受「换设备或清缓存即静默丢失」的不可靠标记。
   为一个无人消费的标记付这个代价不成立。
3. **不做并非不可逆。** 将来若要统计，只影响**增量**订单；历史订单缺标记不是数据损坏。

**重启条件**：出现一个**被点名的消费者**——能具体到「谁看、看什么、据此做什么决定」。
届时本平台自会提出字段与读回接口的需求；且**重启时仍须遵守**下面这条顺序：
**先绑定「商品在该报告的推荐集内」，再启用归因。**

**（将来重启用，以下约束仍然适用，保留备查）** 若届时启用归因，承载它的字段其
**可见性与语义由商城侧决定，可能随版本变化**；因此本平台的归因展示**必须容忍它消失**——
读不到时不影响加购本身，也不报错。

## 阻塞项三：深链给不出完整商品标识

**本平台持有的是 SPU 标识（商品级），而加购需要 SKU 标识（规格级）。**
第三方只读商品端点返回的是 SPU，不返回 SKU；SKU 的解析因此**归商城侧**
（商城商品页本来就要完成这件事）。

所以深链携带 **SPU**；若商城侧要求深链直接带 SKU，请提出——本平台需要先拿到 SKU 列表
的来源，那会改变第三方只读端点的返回面，属另行立项。

## 深链形态

```
GET https://<商城域名>/<加购入口路径>
      ?tenant_id=<租户标识>
      &id=<SPU 标识>          ← 与 spu_id 同值（是否有必要见下方注 1）
      &spu_id=<SPU 标识>
      &quantity=<数量>
      &detection_id=<本次检测标识>
      &exp=<过期时间戳（UNIX 秒）>
      &sig=<HMAC-SHA256 签名，十六进制小写>
```

- `<加购入口路径>`：**待商城侧指定**（见阻塞项一）。
- **`id` 与 `spu_id` 传同一个值**（两者同值，不是两个不同标识）。
  `spu_id` 是本契约的字段名；`id` 是**商城那一侧的参数名**，本平台从已部署的 H5 产物
  里读出过它（`goods-detail/index?id=`）。**两个都带**：这是不出错的保守做法，
  多一个同值参数没有副作用。

  ⚠️ **但「哪个参数名是必需的」尚未确认，下面注 1 说明了为什么。**

  1. ⚠️ **关于「哪个参数名真的生效」，本平台只有「产出物里出现了它」这一条证据**，
     没有做过对照实验。在浏览器里分别试「只带 `id`」「只带 `spu_id`」「两个都带」
     时，**三者都能渲染出商品**（`spu_id` 那次是价格区空白、其余正常）——所以那次
     观察**不能用来断言 `id` 是必需的**。当初那句「只带 `spu_id` 会渲染不出」是在
     同一条街上不同状态的页面上观察到的，不能相减。
  2. **真正要确认的**：商城页面从查询串取商品时读的是哪个参数名。这需要 H5 源码
     （`shopPackage/pages/goods/goods-detail/index`）或让前端团队确认。在那之前，
     两个都带是不出错的保守做法——多一个同值参数没有副作用。

- `detection_id`：本平台侧检测记录的标识。**它不保密**——会随报告回显给患者。
  **因此安全性完全依赖 `sig`，不依赖不可猜测。** 这一条是本契约最重要的约束。

  ⚠️ **签名覆盖 `id` 吗？** 覆盖 —— 待签串是「除 `sig` 外的全部参数」。所以收窄
  `id` 会让旧签名失效，两件事必须同批。

## 签名

- 算法：**HMAC-SHA256**。
- **签名方是 health-flow 服务，不是 genesis-evidence。** 本契约文件托管在
  genesis-evidence 的 `docs/`（与 `docs/condition-to-mall-tag.md` 同类：交付给商城侧的
  词汇表），但**检测记录与商品都在 health-flow**；本仓既不产生也不需要检测标识或 SPU。
  「本平台」在下文一律指 health-flow。
- 待签串：**含路径**——先放一项 `path=<加购入口路径>`（不含域名与查询串），
  其后是除 `sig` 外的**全部参数**按键名 **ASCII 升序**拼 `k=v`，以 `&` 连接，
  **不做 URL 编码**，末尾不追加密钥以外的内容。
  路径参与签名是为了让票据**绑定到它被签发的那个入口**：若商城有多个共用密钥的入口，
  不绑路径时同一组参数与签名可以整体搬到另一入口。
- 参数值先 `trim`；空值不参与拼接。
- 输出：十六进制**小写**，放入 `sig`。
- 密钥**只在本平台（health-flow）与商城之间**持有；交换方式**待商城侧指定**
  （本平台不通过明文信道具传递密钥）。

### 签名担保什么、不担保什么（**请商城侧按此理解**）

`sig` 担保的是**「这份载荷由本平台签发，且自签发后未被改动」**。它**不**担保
「该商品与本报告的健康风险相关」——本平台的签发端只鉴权报告，不校验商品是否落在该报告
的推荐集内。

因此：

- **商城侧不得把 `sig` 当作推荐背书、授权凭据或健康相关性的证明。** 它不是。
- 在患者侧，`sig` 能防的是**传输途中被改**（改商品、改数量、改过期）；它防不了
  「持有报告的人换一个商品标识重新请求」——那个人本来也有权在商城自行加购该商品，
  所以这不构成提权。
- **归因（「来自健康建议」）已决定不做**（见阻塞项二）。本平台不签发归因载荷，
  商城侧也无需接受或持久化它。因此**不存在**本节先前提示的那个风险：既然订单上
  没有「来自健康建议」这个标记，也就没有「伪造归因」可言。
  将来若重启归因，顺序不变——`sig` **必须**先绑定「商品在该报告的推荐集内」，
  且该约束写在本平台自己的交付票里，不在此处对商城侧承诺。

## 过期与失败

- `exp` 为 **UNIX 秒**，有效期 **10 分钟**。**过期校验在商城侧**——本平台签发后无法撤回，
  撤销只能依赖短有效期。
- **`exp` 是安全参数，不得因为「允许二次登录」而延长。** `detection_id` 是**标识符
  不是密钥**（它会随报告回显、会进日志、会被转发），因此任何人都能改写它。
  短有效期限制的是**一张已签发的深链被转发后仍可被用来完成加购的时间窗口**：
  它**不防重放**（同一张链接在有效期内可被反复打开），撤销也只能依赖短有效期。
  （归因不做之后，`exp` 保护的**不再是**一条归因记录——那张记录不存在了。）
  降级后的验收口径只改变「要不要免登录」，**没有**改变「载荷是不可信输入」这一点。
- 由此引出一个**必须由商城侧回答**的问题：允许登录后，登录耗时很可能超过 10 分钟。
  **加购参数如何在登录跳转中保住、以及过期如何处置，待商城侧确认**——它决定方向 A
  是否可用（方向 B 不依赖它）。本平台不自行假定一个续接方案。
- **两类失败必须分清，否则会出现两套说法：**
  - **商城侧拒绝**（过期、签名不符、商品下架、库存不足）：应在商城侧呈现**用户可见的
    原因页面**。本平台在跳转前**无法预知结果**，故不对此负责。
  - **跳转本身失败**（URL 构造不出、密钥未配置）：由本平台**在跳转前**如实提示，不静默。

## 商城侧需要做什么（汇总）

1. 指定 `<加购入口路径>`（阻塞项一的方向 A 或 B）。
2. ~~指定归因字段及其读回接口。~~ **已撤回**——本期不做归因，商城侧**无需**为此做任何事
   （见阻塞项二）。
3. 指定密钥交换方式。
4. 实现 `sig` 与 `exp` 校验，并在拒绝时提供可见的错误页。
5. 解析 SKU（阻塞项三）。
6. **若选方向 A**：确认登录后如何续接加购（参数如何保住、登录耗时超过 10 分钟如何处置）。
   这一条决定方向 A 是否可用。

## 本平台要做什么（尚未实现）

- 构造上述 URL 与 `sig`；**不调用商城任何写接口、不持有购物车状态**。
- 密钥只从环境注入；缺失时**不跳转**并如实提示，不发一个注定被拒的链接。
- 单测钉死：篡改任一参数必须验签失败；`exp` 过期必须失败。
- 前端按钮的落地位置等本契约定稿后再做。

  ⚠️ 同一次实测暴露了「服务端认会话 ≠ 前端认登录态」这个硬阻塞，见「阻塞项一」。
- **「患者在商城侧始终已登录」**：无证据。方向 A 的可用性依赖它，方向 B 不依赖。
- **微信内置浏览器中的深链跳转行为**：未验证。商城 H5 为 uni-app 打包，跳转行为可能与
  普通浏览器不同；本平台的既有经验表明这类差异确实存在（报告页在微信内置浏览器下打印受限，

  其他下单类型（积分、奖品、线下、分销等）是否携带，**未验证**——
  不应假设「任何下单路径都能带归因」。
