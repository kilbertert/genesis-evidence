# 疾病方向 → 商城商品标签：语义映射

本文件把本平台的 `condition_code` 映射为**趣云商城侧的（标签名，标签值）对**。

- 本文件只做**语义层**：哪个疾病方向对应商城的哪个标签对。它是全局词汇表，变更很慢。
- 经营层（某个租户把标签打到自己哪些商品上）**不在本文件**，由商城后台界面完成，无需开发。
- 交付形态就是本张表（Markdown）；**暂不提供机器可读副本**，因此也**没有**自动校验脚本。
  代码里的条件目录（`core/conditions.py` 的 `CONDITIONS`）是本表 12 行的核对依据，
  但不能替代交付物本身。若后续消费方需要可直接加载的格式，那是另一张票的事。

## 为什么是「对」而不是单个标签名

商城侧的商品标签是**两层**结构，实测确认（`cloud-mall-common` 的 `GoodsLabel` /
`GoodsLabelOption` / `GoodsSpuLabel`）：

- `goods_label.label_name` —— 标签名
- `goods_label_option.option_name` —— 该标签下的取值
- `goods_spu_label` 把商品 SPU 关联到 **(label_id, option_id)**

按标签取商品的实现按**字符串精确相等**先解析出 id，再查关联表：

1. 用 `label_name` 查标签；查不到就**静默跳过**（`if (goodsLabel == null) return;`）
2. 在该标签下用 `option_name` 查取值；查不到**同样静默跳过**
3. 只有两者都命中，才用 id 查商品

**结论：只写"标签名"不足以取到商品，必须给出标签名 + 标签值。**

## 验证状态：部分行已跑通，其余仍未验证（2026-09-30 实测）

**结论先写**：映射的**名字**已在商城侧查到对应行（12/12 命中），但
**「按标签取到商品」只在 2 行上真的发生过**。两件事不是一回事，别合并。

### 已核实：12 个（标签名, 取值）在商城侧都存在

用商城 C 端读回接口逐类别查（`GET /mallapi/goodslabel/listByCateName?cateName=<类别名>`
+ `tenant-id` + `client-type: H5`），12 个类别各返回 1 个同名标签 + 1 个同名取值，
字符串与本表**逐字一致**。所以「名字写错」这一种失败已经排除。

### 已跑通：只有 2 行真的取到了商品

`POST /mallapi/goodsspu/getGoodsByLabels`（商城**已有的**按标签取货接口）：

| 取值 | 结果 |
| --- | --- |
| `心血管功能评估` | 命中 1 件（`心腦通`） |
| `肠道健康评估` | 命中 1 件（`排毒消濕寶`） |
| `肾脏功能评估` | `data: null` —— 挂在这两个取值上的商品**都已下架**，被接口自己的可售性过滤剔除 |
| `脂肪肝风险评估` | `data: null` —— 同上 |
| 其余 8 个取值 | 未取到商品（该方向上没有「已上架且已挂标签」的商品） |

**`data: null` 与「名字写错」是同一种沉默**，但这次的成因不是映射错了，而是
**挂在该取值上的商品没有上架**：实测 12 件商品里只有 4 件 `shelf=1`，其中 2 件挂了标签。
所以「取不到」的修法是**上架商品**，不是改本表。

### 因此本表的可用范围

- **可以直接用**：`COND_HYPERTENSION_RISK`、`COND_CHRONIC_CONSTIPATION`（各跑通过一次）。
- **名字已核实、但还没在真实取货上跑通过**：其余 10 行。
- 在这 10 行也各自跑通一次之前，**不要对外宣称「12 个方向都能出商品」**。

### 复现方式（不需要任何凭据）

```bash
curl -s -H 'tenant-id: <租户标识>' -H 'client-type: H5' \
  -X POST -H 'Content-Type: application/json' \
  -d '{"goodsSpuLabels":[{"labelName":"<标签名>","optionName":"<取值>"}],"returnUnion":true}' \
  https://<商城入口>/mallapi/goodsspu/getGoodsByLabels
```

`<标签名>` 与 `<取值>` 是**两个不同的占位符**：本表 12 行的这两个值是**同名**的
（见上节实测），所以填起来看着一样；但那是因为这 12 行恰好同名，不是可以省成一项。

返回 `data: null` 或空数组都表示「没取到」，而不是「接口坏了」——两者的区别见上表。

## 交付说明：本文件如何进入商城侧

1. 交付物是**这一张表**，不是本仓库的访问权。
2. 商城侧按 `condition_code` 查表得到 `(标签名, 标签值)`，用二者过滤商品。
3. **逐字一致**是硬要求。商城按名匹配，未命中静默跳过——**静默**是这里的主要风险，
   因此改名必须与商城侧同批，且改名前后都要有一次真实的"取到商品"验证。
4. 本文件不含租户标识、门店标识或任何凭据，因此可以整份交付；具体租户由调用方指定。
5. 若商城侧最终改为按 id 匹配，本表需加两列 id，并以商城侧实际取值重新核对。
   在此之前按名匹配的失效模式是"静默无商品"，**不是报错**。

## 这个文件不负责什么，以及一个必须说清的边界

- 不做品类 / 批准文号 / 医疗宣称词过滤——那是商城侧的独立工程。
- 不决定返回哪些商品、如何排序、库存与价格的正确性。

**边界（重要，勿默认）**：接入后，患者侧商品展示的**唯一闸门就是商城侧的可售性过滤
（审核通过 + 已上架 + 门店/租户归属）**。本平台此前的产品审核闸门——只展示 `published`
推荐、排除带高风险宣称的产品——会随产品能力退役而**一并消失**（见 #169 / #173）。

这不是疏漏，是一个**已明确记录并接受**的取舍：本阶段由商城承担商品侧的把关，平台侧不再
叠加第二道过滤。因此：

- 商城侧**不得**把"按标签取到商品"理解为"这些商品已经过患者展示审核"；
- 需要医疗宣称词 / 品类 / 批准文号一类的监管过滤时，是**商城侧的独立立项**，
  不是本文件的隐含前提，也不能假定平台侧会兜底；
- 若后续决定在平台侧重新引入审核闸门，那是**新的决定**，需要单独记录，不能靠本文件的措辞沿用。

### 这条边界已由 ADR 0006 确立

上面的边界曾经与本仓库 ADR 0004 冲突，该 ADR 的 Consequences 写着：

> the recommendation engine must never bypass the published-only gate to reach blocked candidates

**该冲突已解决**：`docs/adr/0006-retire-product-capability-and-move-goods-authority-to-the-mall.md`
显式取代了 ADR 0001–0004，把患者侧商品把关的归属写成商城侧的可售性过滤，并明确平台侧
**不再叠加第二道**。ADR 0004 的 published-only 规则是被**取代**，不是被缩窄——商品离开本仓库后
它已无适用对象。

**治理放行不等于内容可用，这两件事到今天仍然要分开说。**

- **治理上已放行**——原先挡着它的冲突解决了，本文件不再"不能作为交付依据"。
- **内容上：12 行的取值都已填、名字都已在商城侧核实存在**（2026-09-30），
  但**只有 2 行真的在真实取货上跑通过**，其余 10 行要等对应商品上架并挂标。
  按名匹配失败是静默的，所以「名字对」不能替代「取到过」。

当前可交付的范围、以及"取不到"的两种成因（名字错 vs 商品没上架），见「验证状态」一节。
