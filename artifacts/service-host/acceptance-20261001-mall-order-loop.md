## 结论

**整条链路跑通了，包括真的下单。**

上一份记录（`acceptance-20261001-health-entry.md`）只验到「深链落到商品页并渲染」，
并如实写明「**没有真的加购下单**」。本记录补上这一段：从健康服务的推荐按钮一路到
商城生成订单。

> ⚠️ **本记录曾把一次测试假象写成「真实缺陷」，已订正。** 初版称「深链落地的页面
> 能看不能买，商城前端不认票据建立的会话」，并据此（在其他文档里）要求商城侧改动。
> **那个结论是错的**，见下节。**商城侧不需要为「登录态」做任何事**——
> 方向的其余商城侧工作（`sig`/`exp` 校验、登录后如何续接加购）不受此影响，仍然成立。

## `user_info` 与 `third_session`：一次测试假象（**订正**）

**初版的错误结论**：深链落地商品页渲染正常，但点「加入购物车」弹「还未登录」，
于是判定「商城 H5 前端不认票据建立的登录态，商城侧必须改」。

**这个结论不成立。** 它来自一次**我自己没搭对的测试环境**：当时的浏览器
**只注入了 `third_session`，没有注入 `user_info`**。

**对照实验**（同一账号、同一租户、同一页面、同一次点击序列，**只变一个量**：
`user_info` 有没有）：

| localStorage 状态 | 结果 |
| --- | --- |
| `third_session` **+** `user_info` | **添加成功**，`POST /mallapi/shoppingcart` 正常发出 |
| 只有 `third_session` | 弹「您还未登录」 |

**而真实登录两个键一起写**（`shopPackage/pages/login/codelogin.vue` 等约 30 处）：

```js
uni.setStorageSync('third_session', userInfo.thirdSession);
uni.setStorageSync('user_info', userInfo);
```

**所以「只有 `third_session`、没有 `user_info`」不是真实登录能产生的状态。**
那个「还未登录」是**测试假象**，不是产品缺陷。

**为什么我当时会读错**：提交分支确实读 `user_info`
（`packageSku.vue` 第一行 `if (!uni.getStorageSync('user_info') || !…id) return …`）——
这一句是真的。但我从它**反推**出一个未经检验的前提「票据会话建立后 `user_info` 为空」，
**没有去看真实登录到底写了什么**。读代码能告诉你它**需要**什么，不能告诉你
真实用户**是否满足**——后者只能实测。

**真实要求是什么**：页面需要 localStorage 里有 `user_info`，即**该浏览器此前登录过商城**。
这正是降级后的验收项「允许一次商城登录」所接受的情形。**方向 A 不需要商城侧改动。**
深链本来就落在**商城自己的域名**上，其 localStorage 天然在作用域内，也不涉及跨源。

**本次验收的加购与下单因此是有效的**：当时写入的两个键，正是真实登录会写的两个键。

**关键点**：从第 18 步到第 24 步全部发生在商城侧，健康服务**没有**调用商城任何写接口。
深链只把用户与参数带到商城，加购与下单由商城自己的页面与会话完成——
这与 ADR 0006（商品权威归商城）和深链契约的边界一致。

## 订单是否带回健康服务归因：**没有**

同上一次核对的结论：商城订单上的 `ext1` / `ext2` / `ext3`、`flowSource` /
`flowSourceId` 在这笔订单上**都是 `null`**。

这与契约现状一致：深链契约里 `sig` 明确**不**担保归因，归因落点在契约里仍是
「待商城侧指定」。**本次下单没有产生任何「来自健康建议」的标记**，属预期。
深链 URL 里的 `detection_id=report-40` 只是被带进了页面，**没有被写进订单**。

## 负向确认

| 场景 | 结果 |
| --- | --- |
| 浏览器里有 `third_session`、**没有** `user_info`（即上文那个测试状态） | 商品照常渲染（取货不需要登录态），点加购弹「还未登录」（**不是**静默失败）。 |
| 深链过期 | 未在本次复测（上一次已确认商城侧拒绝语义；本次链接在有效期内用掉了） |
| 签名被改 | 未在本次复测（同上） |

> ⚠️ **上表第一行是「注入了什么」，不是「真实用户是什么」。** 它测的是**存储状态**
> （`third_session` 有、`user_info` 无），**不是**「第一次来商城的访客」——
> 那种访客浏览器里两个键都没有，本次**未测**。按代码，缺 `user_info` 会被同一句拦下
> 并给出登录入口，但那**不是本次的实测结果**，不要当成已验。

## 遗留与建议

1. **方向 A 不需要商城侧改动**（初版在这里写的「商城前端必须先改」已订正，见上节）。
   剩下的是一条**产品口径**，不是缺陷：未在本浏览器登录过商城的患者点深链，
   会看到「还未登录」并需登录一次——这属于降级后验收项允许的一次商城登录。
2. 归因落点仍未定，本次订单佐证了「不带归因」的现状。
3. 健康服务仍未加域、仍是明文 HTTP（同上一份记录的已知边界，未变）。
4. 本次验收在浏览器里**真实产生了生产数据**（一笔待付款订单），
   若需保持环境干净，请按上文处置。
