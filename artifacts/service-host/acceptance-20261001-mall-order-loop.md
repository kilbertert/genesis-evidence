## 结论

**整条链路跑通了，包括真的下单。**

上一份记录（`acceptance-20261001-health-entry.md`）只验到「深链落到商品页并渲染」，
并如实写明「**没有真的加购下单**」。本记录补上这一段：从健康服务的推荐按钮一路到
商城生成订单。**过程中发现一处真实缺陷**，见下。

> ⚠️ **本次没有修复任何商城代码。** 下面「发现的缺陷」一节里说的「修复」，
> 指**验收时在浏览器里临时补上了登录态**（`uni.setStorageSync('user_info', …)`），
> 以便继续走完加购与下单，从而把链路的其余部分验出来。**商城前端一行未改**，
> 真实用户今天仍然会在这一步被拦下。这条缺陷的修复在商城侧，尚未完成。

## 发现的缺陷：一次性票据建立的会话，商城 H5 前端不认

**现象**：按上一份记录的方式打开深链，商品页**渲染正常**（图集、价格 $480、
库存 100、商品名、买家评价都在），但点「加入购物车 → 确定」时弹
**「您还未登录，请先登录后再进行购买哦~」**，加购被前端拦下。

**根因**（读 H5 源码 + 浏览器实测对照）：

1. `shopPackage/pages/goods/goods-detail/packageSku.vue` 的提交处理第一行是
   ```js
   if (!uni.getStorageSync('user_info') || !uni.getStorageSync('user_info').id)
     return this.isToPage = true;   // 弹「还未登录」
   ```
   **前端只认 localStorage 的 `user_info` 对象**，不看 `third_session`。
2. 商城 H5 的 uni-app 打包把 storage 值包成
   `{"type":"object","data":…}`；**必须用 `uni.setStorageSync` 写**，
   直接 `localStorage.setItem` 写裸值，`uni.getStorageSync` 解不出来。
3. 深链落地时，页面用 `third_session` 调接口**能成功**（服务端认会话），
   但前端逻辑分支走的是 `user_info`，于是「看着像已登录、一动就说不登录」。

**为什么上一份记录漏了**：它验到「页面渲染出商品」就停了。**渲染成功与前端认到
登录态是两件事**——商品数据是服务端按 `spu_id` 取的，不需要登录态。

**本次验收的绕行**（**不是修复**）：在深链落地前，用 `uni.setStorageSync` 同时写入
`user_info`（该账号的登录响应体）。写入后加购一次通过。**这只是让验收能继续走完**——
商城前端未改动，真实用户仍旧被拦。

**这条对契约的含义**（`docs/deep-link-contract.md` 的「阻塞项一」）：
方向 A（「带票据的加购页 URL」）要可用，商城侧必须**从深层链接受的票据/会话建立
前端可读的登录态**，而不只是让服务端认会话。否则用户点过去能看不能买。
这条以前只是被列为「需要商城侧确认」，现在有实测证据说明它**是硬阻塞**。

**关键点**：从第 18 步到第 24 步全部发生在商城侧，健康服务**没有**调用商城任何写接口。
深链只把用户与参数带到商城，加购与下单由商城自己的页面与会话完成——
这与 ADR 0006（商品权威归商城）和深链契约的边界一致。

## 订单是否带回健康服务归因：**没有**

同上一次核对的结论：商城订单上的 `ext1` / `ext2` / `ext3`、`flowSource` /
`flowSourceId` 在这笔订单上**都是 `null`**。

这与契约现状一致：深链契约里 `sig` 明确**不**担保归因，归因落点在契约里仍是
「待商城侧指定」。**本次下单没有产生任何「来自健康建议」的标记**，属预期。
深链 URL 里的 `detection_id=report-40` 只是被带进了页面，**没有被写进订单**。

## 遗留与建议

1. **深链要能真的买，商城前端必须认到登录态**——这是本次最重要的发现，
   已写进「发现的缺陷」。在商城侧给出方案前，方向 A 需要用户「二次登录」才可用。
2. 归因落点仍未定，本次订单佐证了「不带归因」的现状。
3. 健康服务仍未加域、仍是明文 HTTP（同上一份记录的已知边界，未变）。
4. 本次验收在浏览器里**真实产生了生产数据**（一笔待付款订单），
   若需保持环境干净，请按上文处置。
